# 嵌入式 C 项目开发规范

> 来源：`嵌入式C项目开发规范手册` v3.0 (2026-07-23)
> 适用：STM32 / MCU 嵌入式项目（当前: CyberryPotter — STM32F103 + Keil5 + 无RTOS）

## 第一章 项目启动规范

### 🔴 1.1 SDK 版本对齐
- 编码前精确确认 SDK 版本号到小版本（如 STM32F1xx_StdPeriph_Lib V3.5.0）
- 大版本升级前必读 Migration Guide
- 参考示例代码时确认版本标签一致
- 不忽略 deprecated 警告

### 🔴 1.2 硬件管脚对齐
- 新建/移植前制作引脚映射表，标注：Strapping 管脚、仅输入引脚、调试口
- STM32：PA13/PA14 为 SWD 调试口，不得随意占用

### 🔴 1.3 第三方库可用性预检
- 使用前验证组件仓库可访问（非 403/404）
- `grep -r "函数名"` 确认函数签名在当前 SDK 版本存在
- GitHub 超过 2 年未更新的库，做好自行维护准备

## 第二章 编码规范

### 🔴 2.1 类型系统
- **禁止裸 C 类型**，统一使用 `<stdint.h>`：`uint8_t`、`int16_t`、`uint32_t` 等
- **禁止魔数**，所有硬件常量用 `#define` / `enum` 命名
- **禁止浮点运算**，用定点数或整数位移

### 🔴 2.2 内存管理
- **禁止** `malloc/calloc/realloc/free` — 所有缓冲区和结构体编译期静态分配
- 数组/指针传入函数时**必须同时传入缓冲区大小参数**
- **禁止** `sprintf/strcpy`，必须用 `snprintf/strncpy`
- 🟡 `const` 修饰的查表/配置结构让编译器放入 `.rodata` 段（Flash 而非 RAM）

### 🔴 2.3 中断与并发
- ISR 必须极短（<50μs），**禁止**在 ISR 中调用阻塞函数或执行 I/O
- ISR 与普通任务共享的全局变量**必须加 `volatile`**
- 微秒级 GPIO 时序操作**必须用临界区保护**

### 🔴 2.4 位操作与硬件访问
- 位移操作**必须**使用显式位宽字面量：`1UL << 31` 而非 `1 << 31`
- MMIO 指针必须声明为 `volatile uint32_t *const`

### 🔴 2.5 状态机与 switch
- 所有 `switch-case` **必须包含 `default` 分支**
- 状态切换时先保存旧状态再赋值新状态

### 🔴 2.6 可配置化
- WiFi 密码、服务器 URL、API 密钥等可变参数必须通过 Kconfig/sdkconfig 管理，**禁止硬编码**
- 任何可能失败的操作必须有安全默认值

## 第三章 构建与工程管理

### 🔴 3.1 增量构建
- 写完一个模块 → 编译 → 烧录 → 验证 → `git commit` → 再写下一个
- **禁止**一次性写完所有模块再编译
- 推荐开发顺序：可观测输出（LED/OLED）→ 传感器输入 → 交互输入 → 通信/升级

### 🔴 3.2 CMake/依赖管理
- CMakeLists.txt 中只列出实际用到的组件
- 组件命名避免与系统头文件/官方组件重名

### ⚪ 3.3 分区表与 OTA（CyberryPotter 不适用）
- 分区表优先自动布局
- OTA 首要原则：不能变砖，所有失败环节有降级策略

## 第四章 调试与排错方法论

### 🔴 4.1 标准排查顺序
**固定顺序**：日志输出 → 初始化流程 → 数据流路径 → 信号/时序 → **最后才是硬件**
禁止一上来就怀疑硬件。

### 🟡 4.2 日志策略
- 每个组件在 `init` 和关键路径上打印日志
- 分级：`ERROR`（致命）、`WARN`（可恢复）、`INFO`（关键状态）、`DEBUG`（仅开发阶段）

### 🟡 4.3 过度设计识别
- 不为单次使用建抽象层，不加未被要求的灵活性
- 自检：「高级工程师会觉得这个过度复杂吗？」

## 第五章 测试与验证

### 🔴 5.1 移植项目隐式逻辑清单
移植时列出原代码中所有 ISR/HAL 回调/DMA 中断中的逻辑，在新平台显式重建。

### 🟡 5.2 状态切换边界测试
覆盖所有状态转换路径。

### 🔴 5.3 长时间稳定性测试
交付前必须通过**至少 24 小时**连续运行压力测试，期间监控任务栈水位和可用堆内存。

### 🟡 5.4 FreeRTOS 任务审查清单（CyberryPotter 暂无 RTOS）
新增/修改任务后回答：
1. 各任务优先级是否合理？是否会饿死低优先级任务？
2. 同优先级任务是否会产生竞态条件？
3. 是否存在优先级反转？
4. 是否有任务缺少阻塞点？
5. 栈大小是否合理？（通过 `uxTaskGetStackHighWaterMark` 实测后调整）

## 第六章 架构设计原则

### 🔴 6.1 安全默认值原则
任何可能失败的操作，默认行为是**安全降级**，而非阻塞重试或崩溃：
- 网络超时 → 用缓存值
- OTA 检查失败 → 跳过升级
- 传感器读取失败 → 用上次有效值

### 🟡 6.2 单芯片优先
目标芯片已集成所需外设时，优先用单芯片方案。

### 🟡 6.3 半成品模块果断替换
原方案代码不完整或依赖不稳定外部服务时，果断替换而非补全。

### 🟡 6.4 移植时不顺手重构
移植和重构是**两个独立变更**，混在一起 = 同时引入两类变量，定位困难。

### 🟡 6.5 循环依赖处理
用 `extern` 声明替代 `#include` 避免循环依赖，依赖关系单向流动。

## 第八章 看门狗与故障恢复

### 🔴 8.1 喂狗策略（关键）
- 喂狗**只在主循环末尾执行一次**
- **绝不在** ISR、定时器回调或多个位置分散喂狗
- 分散喂狗是头号常见错误：主循环卡死时 ISR 仍在喂狗 → WDT 形同虚设

**正确模式：**
```c
volatile uint8_t task_healthy[TASK_COUNT] = {0};

int main() {
    while (1) {
        if (all_tasks_healthy()) {
            watchdog_feed();  // 所有任务都健康才喂狗
        }
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}
```

### 🔴 8.2 复位原因记录
每次启动时检查复位原因寄存器：
- ESP32：`RTC_CNTL_RESET_CAUSE`
- STM32：`RCC_CSR`
- 启动时打印：「Reset cause: WDT (task X blocked for Y ms)」

### 🟡 8.3 故障分级处理
按严重程度分级响应：可恢复降级 > 重启恢复 > 安全停机。

## 第九章 静态分析与自动化检查

### 🟡 9.1 必查的 MISRA C 关键规则
| 规则 | 说明 |
|---|---|
| 禁止 printf/scanf | 用串口日志替代 |
| 禁止动态内存分配 | 编译期静态分配 |
| 禁止递归 | 嵌入式栈极有限 |
| 禁止未使用的变量 | 清理死代码 |
| if/else 必须用大括号 | 避免悬挂 else |
| 一个函数一个返回点 | 降低控制流复杂度 |
| switch 必须有 default | default 不可为空 |
| 位域必须显式 signed/unsigned | 位域符号由实现定义 |

### 🔴 9.2 集成到构建流程
- 编译警告全部当作错误处理（`-Werror`）
- 预 commit 检查：`make -j$(nproc)` → `cppcheck --enable=all --inconclusive src/`
- 有警告或错误 → 拒绝 commit

### 关键要点（备忘）
- ECDSA NIST P-256 签名短（64 字节），验签快，适合 MCU

## 第十三章 通信协议健壮性

### 🔴 13.1 帧完整性校验 (CRC)
| 算法 | 适用场景 | CyberryPotter 相关性 |
|---|---|---|
| CRC-8 | 短帧 I2C/SMBus | 🟡 传感器通信 |
| CRC-16 | 通用串口/Modbus | 🟡 串口通信 |
| CRC-32 | 固件包文件校验 | ⚪ |

### 🔴 13.2 超时与重传
- 采用**指数退避 + 上限重试**（3 次后报通信失败，进入降级状态）
- 禁止固定间隔无限重试

### 🔴 13.3 心跳保活
- 长连接场景（BLE/TCP/CAN）必须实现心跳：发送方每 T 发 PING，接收方超过 2T 未收到则断开
- BLE 建议 5-10s，TCP 建议 30-60s

### 🔴 13.4 序列号防重放
- 每个上行数据帧带自增序列号（seq），接收方丢弃 seq ≤ 上次有效序列号
- 1 字节（0-255 循环）足够
